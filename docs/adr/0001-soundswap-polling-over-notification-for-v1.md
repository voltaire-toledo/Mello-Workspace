# SoundSwap uses polling, not IMMNotificationClient, for hot-plug/default-change detection in v1

TASK-17's architecture originally called for attempting `IMMNotificationClient` (a COM callback interface) first, falling back to polling only if it proved unreliable. We decided instead to ship polling (~4s interval) as the actual v1 mechanism and defer the notification-based approach entirely.

C# tooling like SoundSwitch implements this trivially because the CLR auto-generates COM vtables and marshals callbacks for any interface a class implements. AHK v2 has no equivalent feature: implementing `IMMNotificationClient` requires hand-building a raw vtable in a `Buffer`, wiring each slot via `CallbackCreate()`, and keeping that buffer alive for the process lifetime — `RegisterEndpointNotificationCallback` holds a bare pointer into it, so premature release is a crash. A maintained community AHK audio library (Ixiko's `Audio.ahk`) writes this interface but leaves it commented out entirely, alongside every other COM callback interface it defines — a signal it's considered too fragile even by an author actively maintaining AHK audio tooling. There's also an unresolved second risk: the callback may fire from a non-AHK worker thread, and AHK's runtime is fundamentally single-threaded.

AC #7 explicitly accepts a documented polling fallback as compliant, so there's no compliance cost to this choice. A low-priority follow-up research subtask remains open to re-attempt the notification approach later, scoped to test both vtable-lifetime safety and cross-thread callback safety.
